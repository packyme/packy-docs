## 一句话介绍

Claude Code 默认开着 **auto-compact**。名字像是在自动压缩上下文、省 Token，但在 1M 上下文的模型上，默认阈值大约是 **967K**——几乎要把窗口撑满才会触发。在那之前，你发的每条消息都会带着越来越长的完整对话历史往返一次。

把阈值调低一点，往往能明显少烧 Token。

## auto-compact 触发时做了什么

触发瞬间，整个对话会被替换成一段简短摘要，之后从这段摘要继续。最近和早期的消息都会进入摘要，**不会单独保留任何一条**。

::: tip 常见误解
很多人以为 auto-compact 会像清缓存一样，满了就悄悄删一点旧消息。实际是**一刀切的全量总结**：代码片段、文件路径、具体决策过程，都会浓缩成摘要里的几句话。
:::

## 真正烧 Token 的地方

压缩本身通常很轻；若提示缓存（prompt cache）仍有效，大部分读取还走缓存价。

真正的问题在 **967K 之前**：Claude Code 每条消息都会带上之前的完整对话历史。对话越长，单次请求的上下文越大，消耗也跟着涨。

::: warning 缓存读取便宜，但不是免费
一条消息带着 500K 上下文，即使其中 490K 走缓存读取，这 490K 仍会计入你的 Token 用量。对话越长，每条消息的基础成本越高。

如果在 400K 就压缩过一次，后面的消息往往只带几万 Token 的摘要，而不是 400K 以上的完整历史——差的是**之后所有消息**的基础成本。
:::

## 一条命令把阈值拉下来

在 Claude Code 里运行：

```bash
/autocompact 400k
```

这会把压缩阈值从约 967K 降到 400K（也是官方建议的一个参考值）。上下文到 400K 就会总结一次，之后从摘要继续，上下文长度回到较低水平。

::: important 代价
细节丢失会来得更早。400K 大约是一段中等长度的开发对话；压缩后 Claude 对具体代码和决策通常只保留概要级记忆。需要长时间保持完整上下文时，400K 可能偏激进。
:::

## 阈值怎么选

| 使用方式 | 建议 |
| --- | --- |
| 短对话为主，一个任务一个会话 | 400K 甚至更低（多为兜底） |
| 长对话，持续迭代复杂任务 | 600K 或 700K，在省 Token 与保留上下文之间折中 |
| 必须完整上下文 | 保持默认，接受后期每条消息更贵 |
